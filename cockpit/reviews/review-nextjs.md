## Issues

1. **`requireUser()` throws; it does not return null or a failure — P4/P5/AC-40 wording is wrong as written**
   - Evidence: `src/actions/shared.ts:6-12` (`throw new Error("Not authenticated")`). Every existing action wraps it in `try { const user = await requireUser(); ... } catch (error) { return handleError(error, msg) }` (`src/actions/job/mutations.ts:13-14,56-58`).
   - Spec says: §1 P4/P5 "calls `requireUser()` first ... returns `{ success:false }`"; AC-40 "with `getCurrentUser → null` the call returns failure".
   - Change: state that each action body is `try { const user = await requireUser(); if (!isCockpitEnabled()) return {success:false,message:"Cockpit is disabled"}; ... } catch → cockpit error mapper`. `requireUser` must be *inside* the try, or an anonymous call surfaces as a thrown error (a 500 / error boundary) instead of `{success:false}`. AC-40 should mock `@/utils/user.utils` `getCurrentUser → null` (the existing convention, e.g. `__tests__/note.actions.spec.ts:27`, `__tests__/apiKey.actions.spec.ts:8`) and assert `success:false` plus no `prisma.*` write call.

2. **`handleError` is the wrong error path for cockpit actions (leaks messages, loses codes, logs the whole error)**
   - Evidence: `src/lib/utils.ts:43-60`: `console.error(error, msg)` then returns `{ success:false, message: error.message }`. It forwards the raw `error.message` (Prisma messages included) to the client and carries no code.
   - Spec says: §6.1 "returns the codebase's `{ success, data?, message? }` shape", §6.4 typed errors (`INVALID_STATE`, `CONFLICT`, `SEND_OUTCOME_UNKNOWN`, `GMAIL_RECONNECT_REQUIRED`), AC-36 no secrets in logs.
   - Change: define in `src/lib/cockpit/errors.ts` a `CockpitError(code, message)` and a `toActionResult(err)` that returns `{ success:false, code, message }` for `CockpitError` and a generic fixed message (no `error.message`) otherwise, logging via `log` from `@/lib/telemetry` (used in `src/app/api/profile/resume/route.ts:14,66`) with the code and status only. Do not use `handleError` in `cockpit*.actions.ts`. Add `code` to the return shape in §6.1; the UI switches on `code`, not on message text. Note the existing shape is not even uniform: `createToken` returns `{success, token, record}` (`src/actions/mcpToken.actions.ts:51-55`), so "the codebase shape" means only `success` + `message`; `data` is the usual payload key (`src/actions/job/mutations.ts` returns `{success:true,data:job}`).

   - Evidence: `src/middleware.ts` matcher `["/dashboard", "/dashboard/:path*", "/api/((?!auth|mcp).*)"]` (codemap §8). A server action POST goes to the URL of the invoking page, and a crafted POST with a `Next-Action` header can target any path.
   - Spec says: §1 P5 "The middleware matcher does not cover server-action POSTs".

Require `getReviewQueue`, `getPackageDetail`, `getAdjacentPackageIds` and every cockpit page (RSC) to call `requireUser()` / `getCurrentUser()` themselves. AC-40 covers actions only; add the pages.

11. **File route and framing headers: precedence is documented, deterministic and testable — "narrow the global source" is unnecessary, but ordering is required**
    - Evidence: `next.config.mjs:5-15` has one global rule `source: "/(.*)"` setting `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`. Next documents (from memory of the docs on `headers`; **[unverified in this repo]**) that when several `headers()` entries match a path and set the same key, the **last** matching entry wins (no duplicate headers are sent). So a later scoped entry for `/api/cockpit/files/:packageId` with `X-Frame-Options: SAMEORIGIN` overrides `DENY`.
    - Spec says: §4 "Precedence ... must be verified ... if the global rule wins, narrow the global `source`"; AC-37.
    - Change: replace with a deterministic instruction: the scoped entry is appended **after** the global entry in the array; AC-37's config test asserts the array order and the evaluating logic (last-match wins), and the Phase-4 `curl -I` check asserts exactly one `X-Frame-Options: SAMEORIGIN` header. Also: (a) `nosniff` is already global, so the route's own `nosniff` is redundant but harmless; (b) `Content-Security-Policy: frame-ancestors 'self'` from config **and** `Content-Security-Policy: sandbox` set by the route handler are the same header key; if both are emitted as separate headers browsers intersect them (OK) but if config overrides the handler's value you lose `sandbox` **[unverified which wins for route handlers]** — combine into a single value in one place: `Content-Security-Policy: sandbox; frame-ancestors 'self'` set by the route handler only, and keep only `X-Frame-Options: SAMEORIGIN` in `next.config.mjs`. Note `sandbox` without `allow-same-origin` gives the framed PDF an opaque origin; with Chrome's PDF viewer this commonly shows a blank frame — you already flag it (§11); make AC-30 the gate **before** the UI work, not at the end.

## Conventions summary (follow these)

- Actions: `"use server"` first line, only async-function exports; `try { const user = await requireUser(); ... } catch (e) { return toActionResult(e) }`; import `requireUser` from `./shared`; never `handleError` for cockpit (it leaks `error.message`).
- Return shape: `{ success: true, data }` / `{ success: false, message, code? }`; `revalidatePath` after writes (as in `src/actions/job/mutations.ts`).
- MCP: one `registerCockpitTools(server, auth)` file under `src/lib/mcp/tools/`, one guarded call in `route.ts`; schemas export `XInputShape` + `XSchema`; scope check first, then rate limit, then DB; errors `isError:true` with `"<CODE>: <msg>"` (new style, deliberately different from `route.ts`).
- Rate limit: extend `checkMcpRateLimit(key, max?, windowMs?)` (backward compatible); general limit is 60 / hour / user, in memory, per process.
